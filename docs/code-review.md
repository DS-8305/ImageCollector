# Independent code review

Implementation disposition: all six findings below were subsequently fixed by the implementer and covered by RED-to-GREEN regression tests. The full 129-test suite passes. See docs/verification.md for fix descriptions and exact tests. The following is the original independent report, not a second review of the fixes.

Reviewed the uncommitted implementation on 2026-10-13 against the design, plan, integration consumers, and recovery/download tests. Production code, index, and branch were not changed. The supplied baseline log records **122 tests passed in 17.504s**; it predates the new regression tests being added during this review. No full-suite rerun was performed.

## Important findings

1. **[P1] Preserve the selected candidate set in the run record.** `image_collector/gui.py:362-364` passes the selected candidates only through an in-memory `StaticProvider` closure. `gui.py:382-383` resumes with the default search provider, and `RunStore.create` persists no selection. Select one candidate, let its download fail, then resume: the collector searches again and can save an image the user never checked. A focused production-runner probe reproduced `failed -> success` with saved source `https://unselected.example/page`, although the original selection was `https://chosen.example/page`. Persist the exact candidate objects/URLs and reuse them for resume and retry.

2. **[P1] Reserve image names against files already on disk.** `image_collector/storage.py:277-278` allocates names from manifest records alone, while `storage.py:248` removes the filename from a corrupted record and `storage.py:288` replaces the destination unconditionally. Put an unrelated `image_01.png` in a job folder before its first save: the next commit replaces it. Alternatively, corrupt the only saved `image_01.png`, resume, and save another candidate: recovery erases its reservation and the corrupted file is overwritten. Both cases lose prior output. Check/reserve existing filenames and preserve rejected file reservations; publication must not silently replace an unrelated destination.

3. **[P1] Make stale-lock takeover exclusive.** `image_collector/storage.py:212-218` reads a stale owner and later unlinks the path without proving it still represents that owner. After a crashed run, start two resumes: A reads the dead owner and pauses; B removes it and acquires a new live lock; A resumes, removes B's lock, and also acquires. A deterministic scheduling probe patched only the process-liveness boundary and produced `[('second', True), ('first', True)]`; both stores believed they owned the lock. They can then overwrite the same manifest and images. Use an OS-backed exclusive lock or another takeover mechanism that cannot delete a replacement owner's lock.

4. **[P2] Keep the visible verification browser usable.** `image_collector/runner.py:157-159` records `NeedsAttention`, then `runner.py:181` closes Chrome unconditionally; `image_collector/gui.py:153` does the same during preview. Run visible Google collection or preview against the captured verification page: detection immediately unwinds and quits Chrome. The user cannot inspect/complete the challenge or continue the same run, contrary to the visible-browser recovery flow. Add a cancellable visible-browser attention state while preserving headless checkpoint-and-exit behavior. This finding concerns lifecycle after detection, not whether Google allows collection.

5. **[P2] Enforce deadlines and cancellation while a body trickles in.** `image_collector/downloader.py:228-229` checks its budget only after `iter_content(64 KiB)` yields. A server sending a few bytes more frequently than the socket inactivity timeout can keep that read active until 64 KiB arrives or EOF, postponing both the keyword deadline and a stop request indefinitely in practice. Reproduce with an HTTP response declaring a body above 64 KiB and sending one byte every interval shorter than the read timeout; request cancellation or let the deadline expire. The collector and GUI shutdown remain waiting inside the read. Existing tests send complete 64 KiB chunks and do not cover this case. Use reads/transport control that permits enforcing an overall deadline and observing stop requests during slow responses.

6. **[P2] Do not shorten a valid server Retry-After.** `image_collector/downloader.py:151` caps valid delays at five seconds. A `429` with `Retry-After: 3600` and a 30-second remaining budget therefore retries after five seconds instead of declining a wait that cannot fit. The direct parser probe returned `5.0`; a focused transport-boundary probe reproduced three attempts with requested waits `[5.0, 5.0]`. This disregards the server's rate limit and can prolong blocking across candidate downloads. Preserve the actual delay and stop/reject when the remaining budget cannot accommodate it.

## Considered but declined to judge

- Live Google result-card/detail extraction, source/image correspondence, and filtered results: the observed external page was a verification block. Controlled Chrome fixtures establish fixture behavior, not current allowed live search behavior.
- Live SerpApi quota/pagination/filter correctness: no authorized live account/key was available; provider boundary doubles do not prove the service's current behavior.
- Image reuse/license permission and guarantees that a returned original URL is the publisher's maximum-resolution upload: outside the collector's verified contracts.
- Legacy private GUI helper caching and formatting polish: modern GUI actions use fresh snapshots; no important production trigger was established for those private compatibility helpers.
- Broad adversarial manifest fuzzing and operating-system crash/durability guarantees: path checks and intended rename/checkpoint recovery were inspected, but exhaustive malformed-field and power-loss testing was not performed.

The local HTTP Retry-After probe was blocked by the execution sandbox before reaching the server; the reported Retry-After evidence comes from the deterministic parser and transport-boundary probes. Disposable filesystem probes used `.test-tmp` and cleaned their generated run folders.
